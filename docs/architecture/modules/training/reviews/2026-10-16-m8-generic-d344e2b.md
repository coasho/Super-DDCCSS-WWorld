## Findings

### 1. P2 — compare the captured Python contracts, not only their names

Location: tools/ma_contract/baseline.py:749-757, especially line 754.

PY_INVENTORY records signatures, enum values, named-tuple field order, class members/property kinds, exception bases and qualified runtime owners. The new comparator only asks whether each attribute name still exists. Changing a description while retaining its name therefore passes.

Independent comparison-only probes changed a function signature, an enum value, record field order and a runtime owner separately. Every case returned exit 0 with no failure. These probes stub only the capture step to isolate the actual comparison logic; they do not claim that the installed SDK itself has those mutations.

Required correction: compare every frozen description according to its contract, permitting explicitly additive members without ignoring changes to existing entries. Preserve runtime type owners and public qualified identities. Add meaningful negative cases for signatures/defaults, enum values, record fields, class member kinds and ownership, as well as a permitted-addition control.

### 2. P2 — require fresh artifacts for every selected build

Location: tools/ma_contract/baseline.py:715-719, 731-744 and 749-752; Capture.exports:288-300 and 332-339.

Missing native/Python artifacts are skipped without failing. Reused work directories are not isolated or cleared before capture, so an omitted artifact can also be read from an earlier run. Optional Release omission is a legitimate separate case; missing artifacts in a selected headless/Release configuration are not.

The real CLI was run with a nonexistent --headless-build and a fresh --work. It returned exit 0, reporting 17 comparisons/0 failures while skipping every native/Python build artifact and comparing only freshly compiled header metadata. The isolated comparison probes also show stale outputs being accepted when capture produces no replacement.

Required correction: define mandatory inputs for selected configurations, fail on missing/failed captures, and consume only outputs proven to belong to the current invocation. Keep the frozen baseline read-only. Add missing-DLL/package/extension and stale-work negative regressions; intentionally unselected optional configurations may be reported separately.

### 3. P2 — bind the Python joint replay to installed aircraft data

Location: cmake/RunMissionPackageConsumer.cmake:141-143 and tests/mission_package_consumer/ma_python.py:304. The existing resolver behavior is in src/io/AssetResolver.cpp:68-97.

The Python harness clears FSIM_AIRCRAFT_PATH. The installed library still contains its intentional development source-aircraft search path, which precedes packaged custom aircraft when no explicit aircraft directory is supplied. The main chain's F-16C can therefore come from the checkout even while the DLL and Python package correctly come from the installation. Checking copied files alone does not establish which resource was loaded.

Independent fault injection used only the gate-owned installed Python aircraft XML:

| Installed F-16C XML | Aircraft resolution | Result |
| --- | --- | --- |
| Original | Current harness defaults | Joint episode created, exit 0 |
| Invalid XML | Current harness defaults | Joint episode still created, exit 0 |
| Same invalid XML | Explicit installed aircraft/stores paths | Correctly refused, exit 2 |

The original installed bytes were restored in finally and their SHA-256 rechecked. No source aircraft or generated source artifact was modified.

Required correction: supply the installed Python package's aircraft/stores paths to both parent and isolated child, verify owned runtime-data hashes, and require an installed-resource corruption/missing-data probe to fail without source/build fallback. Retain the intentional development resolver behavior; fix the acceptance harness rather than changing global resolution semantics.
